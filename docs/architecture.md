# Architecture

## System goal
Build a sales intelligence platform that takes internet-facing infrastructure telemetry, ranks companies by likely cybersecurity need, and gives the sales team an evidence-backed account brief.

## Core architecture

### 1. Raw data layer
RAW.SHODAN_EVENTS
- immutable source record in VARIANT
- stores the original ingestion payload
- preserved for debugging, replay, and lineage

### 2. Core event layer
CORE.INFRASTRUCTURE_EVENTS
- typed IP, port, hostnames, domains, organization, ISP, ASN, timestamp, geography, HTTP status, banner, module
- normalizes messy source data into structured fields
- provides the canonical event level used by downstream logic

### 3. Feature layer
FEATURES.ACCOUNT_FEATURES
- account aggregation and signal counts
- converts event-level data into account-level signals such as risky services, cloud hosting, distinct IP counts, legacy protocols, technologies, and recent observations

### 4. Scoring layer
FEATURES.ACCOUNT_SCORES
- deterministic priority score and HIGH/MEDIUM/LOW tier
- score is not generated by the LLM
- score is explainable, auditable, and stable enough for sales prioritization

### 5. AI layer
AI.ACCOUNT_BRIEFS
- evidence-grounded AI output
- summarizes why an account matters, the likely pain points, buyer personas, and outreach angle
- uses structured evidence from Snowflake, not free-form assumptions

### 6. Observability layer
OBSERVABILITY.LLM_CALLS
- request id, timestamp, feature, model, prompt version, request, response, latency, estimated tokens, cost, decision
- supports tracing, debugging, and comparing prompt versions over time

### 7. Application layer
APP
- local Streamlit app used for development and debugging
- Cloud-ready Streamlit app used for hosted deployment
- Snowflake-hosted Streamlit app is also an option when Snowflake AI capabilities are available

## Design rule
Preserve raw data, flatten common fields, aggregate before AI, and keep analytical truth separate from generated text.

## Rule-vs-LLM split
Rules are used for:
- account scoring
- signal aggregation
- tiering
- evidence extraction
- reproducible prioritization

LLMs are used for:
- narrative summary
- why-now explanation
- why this account may matter to a salesperson
- buyer persona suggestions
- outreach angle drafting

This split is important because the core ranking should remain deterministic and explainable, while the AI layer handles interpretation and communication.

## Cost model
The client explicitly asked for cost visibility. We should include a section that explains model selection and cost ceilings.

### Recommended cost math
- cost per request = input_tokens * input_price_per_token + output_tokens * output_price_per_token
- monthly cost = cost per request * requests per month

### Recommended model split
- cheap model for classification or structured extraction
- stronger model for final judgment or nuanced summary generation

### Example production guardrails
- cap requests per account
- use low-cost model for first-pass filtering
- reserve stronger models for top-scoring accounts only
- track average input/output token counts per request
- set a daily or monthly cost ceiling

## How to test the cost model
1. Run the app on a sample of accounts.
2. Log prompt size, latency, model used, and output length.
3. Compute average tokens per brief.
4. Estimate cost per account and cost per 100 accounts.
5. Compare v1 and v2 prompts for token efficiency.
6. Document the operational ceiling for production usage.

## Final design conclusion
The implemented system is a hybrid architecture that is practical for a client submission:
- Snowflake provides the deterministic data and scoring layer
- Streamlit provides the interface
- external AI provides the explanation and outreach layer
- evals, skills, prompts, and observability show this was built as an AI-native workflow rather than a prompt bolted onto a dashboard
